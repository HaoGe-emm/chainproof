# ChainProofVersionRegistry — executable 4B spec

Scope: Solidity `^0.8.20`, compiled using exactly 0.8.20. Independently deployed only to local EVM in this stage. No proxy, token, NFT, admin or public-network address. Existing `ChainProof.sol` and its ABI/business logic are unchanged.

## State / IDs

`originalRegistry: IChainProof immutable` is supplied at construction, must contain code, and must answer a consistency-checked `getProof(bytes32(0))` probe. Probe cannot establish that a malicious conforming implementation is truthful. Trusted source/deployment binding is separately verified by local tooling.

`nextWorkId: uint256 = 1`; monotonic global IDs, 0 is invalid. It advances only on successful atomic creation. Frontend reads the emitted ID rather than guessing it; another user's transaction may allocate a preceding ID.

`Work { address controller; uint64 createdAt; uint64 versionCount; }` is keyed by work ID. Controller and time never change; count only increases. The ID need not be stored again in the struct. Work occupies two storage slots (controller/time packed, count in second slot).

`Version { bytes32 fileHash; uint64 previousVersionNumber; uint64 associatedAt; }` is keyed by `(workId, versionNumber)`; two slots, packed predecessor/time. Number starts at 1. First parent is 0; N points to N-1. Original owner/time remain in the old registry and are read separately, not accepted as arguments or redundantly stored. `linked[workId][hash]` records per-work uniqueness.

No title/description/label/claimed creation time/metadata digest is on-chain. Registration time, association time and creation claims are different concepts. Count/association timestamp bounds are checked; uint256 ID increment is Solidity-checked. No write function loops over history.

## Functions / ABI

| Function | Behavior |
| --- | --- |
| constructor(address original) | Bind one immutable compatible original registry; invalid address/probe reverts. |
| createWork(bytes32 initialFileHash) → uint256 | Validate old proof exists with nonzero time and owner == sender; atomically allocate own work and Version 1. |
| addVersion(uint256 workId, bytes32 hash, uint256 expectedPreviousVersionNumber) | Existing work, controller == sender, old proof exists/owner == sender, unique hash, current count == expected parent; append next ordinal atomically. |
| getWork(uint256 workId) → Work | Return canonical controller/time/count; invalid work reverts. |
| getVersion(uint256 workId,uint256 number) → Version | Valid work and number 1..count; return immutable entry. |
| getVersionCount(uint256 workId) → uint256 | Validate work, return count. |
| isHashLinked(uint256 workId,bytes32 hash) → bool | Validate work and report exact per-work membership. |
| originalRegistry(), nextWorkId() | Read bound address and next allocation. |

`lib/version-registry-abi.ts` is generated by the pinned compiler. Event-only typed frontend ABI must match compiler events; security tests check that identity. `IChainProof.getProof(bytes32)` matches original compiled owner:uint160/address, timestamp:uint256, exists:bool outputs. Old proof registration is never invoked by V2.

## Events

`WorkCreated(uint256 indexed workId,address indexed controller,bytes32 fileHash,uint256 versionNumber,uint256 timestamp)`.

`VersionAdded(uint256 indexed workId,address indexed controller,bytes32 indexed fileHash,uint256 versionNumber,uint256 previousVersionNumber,uint256 timestamp)`.

Creating a work emits both events for ordinal 1. Subsequent append emits VersionAdded. Three indexed parameters in VersionAdded allow work/wallet/hash filtering. Timestamp is block association time; old registration time comes from old getProof. Off-chain discovery preserves block/log order and uses deployment-bound ranges; canonical state remains the authority for full history.

## Errors

`InvalidOriginalRegistry`, `OriginalRegistryUnavailable`, `OriginalProofNotFound`, `NotOriginalRegistrant`, `WorkNotFound`, `NotController`, `HashAlreadyLinked`, `UnexpectedPreviousVersion`, `VersionOutOfRange`, `IntegerLimit`.

Solidity decoding of malformed external return data can revert before a custom error is decoded; it still reverts all state. Frontend reports a readable unavailable/error state, never success. A mined reverting transaction emits no creation/association events.

## Invariants / trust

1. Only controller appends, and controller must be original proof registrant for each hash. A wallet forwarding through another contract cannot spoof the sender.
2. Counts, parent numbers, unique per-work membership and stored entries agree after every successful call. Failed calls change none of them; no ID gaps from failed creations.
3. History and controller cannot be edited/deleted/transferred. Same authorized hash may occur in another work.
4. Original proof owner/time are external facts from one immutable registry; its honesty/availability/code and chain execution remain trust dependencies.
5. No supplied address/time/signature can bypass ownership. STATICCALL happens before writes; mutation/reentrancy into writing methods fails in the static context.
6. Wallet-established association and ordering do not establish copyright, identity, originality, actual creation date or causal derivation of bytes.

Original mainnet register/getProof, My Proofs and `/proof/[hash]` remain independent. A future separately approved V2 may reference existing mainnet hashes; it cannot change their owner/time or backdate a new association. Local copies/relations are never public-chain proofs.

## 4C-1 clarified boundaries — 2026-10-12

This review leaves the contract, ABI, storage layout and authorization semantics specified above unchanged.

- **Constructor assurance:** nonempty code plus a compatible zero-hash tuple is a consistency probe, not a proof of genuine ChainProof identity. A conforming dishonest implementation can satisfy it. The deployer must independently verify the original contract's chain, address, code and absence of unexpected upgrade paths before fixing the immutable reference.
- **Timestamp assurance:** writes require `exists == true`, nonzero original timestamp and `owner == msg.sender`. They do not check that the external registration timestamp is at most the current block timestamp. Honest original ChainProof uses its own block time; a malicious-registry fixture can report a future time and be accepted. V2 association time is still derived internally from its execution block. The local timeline separately rejects an original time later than the association time.
- **Zero hash:** bytes32(0) has the same authorization semantics as any other key. It fails when unregistered and succeeds if the original registry legitimately records it for the sender. Acceptance is not a claim that an actual file with that digest is known. No zero-hash prohibition was silently added.
- **Ordering / replay:** the expected predecessor is mandatory for append. When two queued transactions target the same current predecessor, one can succeed; the other reverts after the count changes. A mined revert contributes no version entry or association event. Transaction replay protections supplied by the chain do not replace this application-level ordering check.
- **Limits of authority:** registry output authenticates registration-wallet equality only under the genuine-registry assumption. It cannot authenticate a person, establish copyright, distinguish copied public files or prove one version was derived from another.

The 4C-1 local EVM suite passed 23 tests, including a 240-action multi-wallet state model, direct bypass attempts, queued competing appends and malicious dependency counterexamples. These tests substantiate bounded behavior; they are not a third-party audit. Compiler settings remain Solidity 0.8.20, optimizer 200, Shanghai. Target BOT opcode compatibility and public deployment approval remain outstanding.
